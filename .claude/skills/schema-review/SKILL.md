# 表设计评审四连问

> 背后的事故：一个字段两处按不同含义使用（坏账号被反复选中）；平台账号写进了指向
> 租户账号表的外键；Stripe 状态枚举漏了一个值导致回调死循环；派生值存了、原始值丢了，
> 后来只能加列 + 全量重爬。表结构是全项目返工最贵的地方。

## 触发条件

设计新表、加列、改字段类型或含义、加约束——任何 DDL 之前。

## 四连问（逐条书面回答，交给用户过目）

1. **每个字段是不是只有一个含义？**
   列出每个字段的「谁写它、谁读它、按什么语义」。同一字段被两个消费方按不同语义读 → 立刻拆成两个字段，不许用注释凑合。
2. **每个外键指向哪张表？查过了吗？**
   逐个外键写出目标表名。系统里存在名字相近的两套实体（如租户账号 vs 平台账号）时，必须查实际约束确认，不许凭列名直觉。
3. **存的是原始值还是算出来的值？原始值还要不要留？**
   时间戳、原始文本这类**事后不可重建**的输入，默认保留。
4. **枚举/状态字段的取值是不是全集？**
   对接外部系统（如 Stripe webhook）时，取值范围必须覆盖**对方文档的全部取值**，漏一个 = 写入失败 + 重投死循环。

## 附加检查

- 加列时：按表名搜索全仓（含定时任务/边缘函数目录），列出**全部写入点**，逐个确认新列有人写。
- 建表时：顺手给外键和常用查询路径建索引（空表时零成本，别假设外键自带索引）。

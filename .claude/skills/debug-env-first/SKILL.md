# 排障先查环境（四查）

> 背后的事故（每个都浪费过半天以上）：shell 全局导出的同名环境变量盖掉了项目配置，
> 「key 对却像没登录」；npm 静默装了两份互不兼容的核心库；改了扩展源码没重新构建，
> 测了半天旧代码；端口残留昨天的旧进程，在旧代码上「测出」假 bug。

## 触发条件

症状属于以下任一类，先走本流程再怀疑业务代码：

- 「配置明明是对的，行为却像没配置」
- 「改了代码，怎么没效果」
- 「昨天还好好的，今天不行了」（但没人改过相关代码）
- 数据莫名为空 / 权限莫名不对

## 四查（按序执行，每查都留证据）

1. **查环境变量覆盖**：`env | grep <相关键名>`——shell 全局导出的同名变量会盖掉项目 `.env`。对比值的长度和前缀是否符合预期。
2. **查依赖重复**：`npm ls <核心包名>`——配套包版本不匹配时包管理器会静默嵌套第二份，两份互不兼容且类型检查不报错。
3. **查构建产物**：确认改动真的进了产物——看构建时间戳，或在产物里搜一个新加的符号。「我记得我构建过」不算证据。
4. **查端口进程**：`lsof -i :<端口>`——确认在跑的进程是刚启动的那个（看 PID 和启动时间），不是昨天残留的。杀进程后确认真的退出了再重启。

## 完成标准

四查全部有结论（每条写「查了、结果是什么」）之后，才允许开始改业务代码。
